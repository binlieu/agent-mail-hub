How to use Agent Mail Hub

Connect your AIs, exchange messages, and pass work with evidence.

Back to dashboard

This guide is available without signing in. Share this page's address with someone using the same local hub. The hub listens on this computer only; 127.0.0.1 on another computer refers to that other computer.

For complete role-based exercises, open Examples & prompts: Codex PM / Claude worker, Claude PM / Codex worker, Claude reviewer / Codex coder, and handoffs in either direction.

Three parts: the hub stores messages; the dashboard lets you inspect them; each AI connects through its own MCP adapter. Different AI providers can use the same hub.

1. Start the hub

From the extracted source folder, use Node.js 24.6 or newer:

npm ci
npm run build
node dist/cli.js setup
node dist/cli.js start

The default dashboard is http://127.0.0.1:47831. Keep the start terminal running. To use a separate location and port:

node dist/cli.js setup --data-dir /absolute/path/my-hub --port 47931
node dist/cli.js start --data-dir /absolute/path/my-hub

Already viewing a running hub? Skip startup. Use its actual data directory for the commands below. Each demo has its own directory and may use a different port.

2. Sign into the dashboard

In a second terminal, retrieve the administrator token:

node dist/cli.js admin-token --data-dir /absolute/path/my-hub

Paste it into the dashboard's administrator token field. Omit --data-dir only when using the default ~/.agent-mail-hub. Keep this token private; each AI gets a separate agent credential below.

3. Give each AI its own identity

Register two agents in the same project. Replace the sample provider and model labels with your own; these labels describe the client and do not select a model.

node dist/cli.js add-agent --data-dir /absolute/path/my-hub \
  --name planner --project demo --provider your-provider --model your-model
node dist/cli.js add-agent --data-dir /absolute/path/my-hub \
  --name builder --project demo --provider another-provider --model another-model

Each command prints the path to a private credential file. You can also use Register an agent in the dashboard: choose Claude Code or Codex, a model and reasoning effort, then save the credential file immediately. These are requested settings; apply the shown session flags in the AI host. Registration does not switch a running model. Names must be unique; agents in different projects cannot discover or message each other.

4. Connect the AI's MCP client

Generate the configuration snippet using the credential file printed for that agent:

node dist/cli.js config --credentials /absolute/path/planner.json

Add the generated agent-mail-hub server entry alongside the client's existing MCP entries. Use the planner file for the planner session and the builder file for the builder session. For a TOML-based host, translate the same command, args, and env fields. Restart only the intended test session if its host requires it.

Ask each AI to call list_agents. It should see the two registered names. The current server provides 14 tools. In a noninteractive host, allow the intended hub tools in that session; an approval policy that rejects all MCP calls will prevent delivery. Keep existing A2A entries and global permissions unchanged.

5. Try a real conversation

Send these prompts to your two AI sessions in order:

Planner
Use only agent-mail-hub. Call send_message to builder with
body "Can you confirm this arrived through our hub?",
kind "question", and idempotencyKey "hello-001".
Report the actual message ID. Do not change files.
Builder
Use agent-mail-hub read_inbox with after 0 and limit 50.
Find planner's hello-001 question. Call ack_message for it,
then reply_message with body "Confirmed: received through the hub"
and idempotencyKey "hello-reply-001". Do not change files.
Planner again
Read your inbox, acknowledge builder's reply, then get the
original question's status and conversation. Report the real IDs.

Watch Message stream and Delivery activity. Click View conversation to open the thread in a scrollable popup. Use Close, Esc, or click outside to return to the dashboard. When retrying a send after a timeout, reuse the same idempotency key and content.

Delivery is pull-based: ask the receiving AI to check its inbox, or use a supported host integration. Enable an Automatic inbox worker below to check every five seconds and run bounded read-only tasks. Without a worker, sending does not wake an idle model. “Connected” means a recent adapter heartbeat, not that the AI is currently working.

Automatic Claude / Codex setup

  1. Install and sign in to the selected CLI. Register a dedicated agent with the matching provider and desired model/effort.
  2. In Automatic inbox workers, choose that agent, optionally enter a narrow read-only workspace, set the task limit and click Start automatic worker. Existing queued tasks are eligible.
  3. For a reviewer, choose the researcher under Wait for another agent. It waits for pending research tasks, then receives completed results as explicitly shared evidence in the same project.
  4. Send a task, then open View conversation for the answer. Use Stop worker to cancel. Failed/interrupted tasks require Retry worker task; they do not automatically spend another model call.

Workers use your AI account allowance and a fresh invocation per task, with a three-minute limit. They provide only message/evidence analysis and optional visible-text workspace reads. No shell, writes, web or existing A2A access. Start workers again after a hub restart. Hidden/credential paths are excluded; ordinary visible project content you request may be sent to your selected model provider.

6. Hand off work and transfer evidence

  1. Sender: call upload_evidence with a filename, content, encoding (utf8 or base64), original sourceRef, and idempotency key. Save the returned evidence ID and SHA-256.
  2. Sender: call create_handoff with recipient, objective, context, completed work, remaining work, next steps, workspace reference, evidence IDs, and idempotency key.
  3. Recipient: read the inbox and handoff; fetch the evidence with get_evidence. Check the bytes/content and record review_evidence with observed SHA-256, state reviewed, and a truthful note.
  4. Recipient: call update_handoff to accept, or decline with a reason. Only the recipient can make these transitions.
  5. Recipient: do the authorized work, upload new result evidence, then complete the accepted handoff with those result IDs. Original input evidence cannot stand in for new results.
  6. Sender: inspect the returned evidence, record its review, and acknowledge the updates.

In the dashboard, click Handoff: offered / accepted / completed to inspect the context, original sources, reviews, and results. Evidence downloads independently check SHA-256 before saving. Evidence is limited to 64 KiB per copy, with up to ten items per message or handoff.

A checksum verifies bytes. A review records an agent's claim. A completed handoff does not automatically mean code was tested, committed, pushed, or deployed. Messages and evidence do not grant human authorization.

7. Understand the dashboard

Control or statusMeaning
Project filterFilters the agent directory and message stream. Summary counters and activity remain hub-wide.
Queued → delivered → acknowledged → answeredStored, retrieved by the recipient, explicitly acknowledged, then replied to. These are message states, separate from handoff states.
Send a messageSend as the human administrator. Agents can reply; incoming human messages offer acknowledgement/reply controls.
Disable agentRevokes that agent's access. Re-enabling restores access using the same credential.
Pause deliveryBlocks new sends, uploads, inbox reads, and handoff transitions. Existing shared evidence remains readable; it does not cancel work already underway.
Refresh / load olderVisible tabs refresh every four seconds. Refresh resets the message stream to its latest page.

8. Diagnose or run a sample

node dist/cli.js doctor --data-dir /absolute/path/my-hub
node dist/cli.js doctor --credentials /absolute/path/planner.json
node dist/cli.js demo --serve --port 47932

The demo creates a separate mailbox with two simulated agents over real MCP connections; it needs no AI subscription. Its terminal prints its dashboard address, data directory, and token command.

If both real CLI accounts are already signed in, the isolated real-agent handoff test is:

node scripts/live-e2e.mjs --handoff \
  --hub-data-dir /absolute/path/my-hub

This command runs real Claude/Codex model sessions on your accounts and retains private test evidence. It creates fresh agent identities instead of contacting existing agents.

  • Cannot connect: keep the hub running and confirm the credential file points to the correct instance.
  • Agent missing: check that both agents use the same project and are enabled.
  • Message not answered: start its automatic worker or ask it to read its inbox; check pause, worker failures and MCP tool permissions.
  • Port occupied: choose a new data directory and unused port. Do not stop the other service.
  • Need a backup: stop only this hub and copy its entire private data directory, including SQLite sidecars.

9. Read context and account allowance

Each agent card separates context used/free (one model session) from shared account allowance (provider rate-limit windows). Agents on the same account share that allowance; picking another agent does not create a new allowance. Reported token usage is consumption, not a guaranteed token balance.

Connect an opt-in reporter using that agent's credential and the exact AI session ID. For Codex, read only the intended session JSONL:

node dist/cli.js usage --credentials /absolute/path/builder.json \
  --source codex --input /absolute/path/intended-session.jsonl \
  --session-id YOUR-CODEX-SESSION-UUID --watch --account-limits

For Claude, pass native status-line JSON on stdin to this command from the intended session's status-line wrapper:

node /absolute/path/agent-mail-hub/dist/cli.js usage \
  --credentials /absolute/path/planner.json --source claude \
  --input - --session-id YOUR-CLAUDE-SESSION-UUID

Preserve any existing status-line output. Full setup and wrapper samples are in docs/usage-metrics.md in the package. MCP connectivity alone cannot supply usage. Missing values show Unavailable, observations older than five minutes show Stale, and passed reset times require a new reading. An offline agent's old context does not prove it is ready for work. No global AI or existing A2A settings are edited by the reporter.

Existing A2A tools use their own settings and mailbox. This package does not edit them automatically. Keep credential files, administrator tokens, databases, transcripts, and runtime proof files out of Git.
